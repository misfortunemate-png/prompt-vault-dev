## 1. 目的

prompt-vault のクラウド同期機能を改修する。改修の柱は二つ。

1. **同期対象のフォルダ選択** — フランの画像フォルダのうち、どのフォルダをクラウドへ同期するかをユーザーが選べるようにする
2. **クラウド画像の軽量化** — クラウドに保存する画像を、モバイル端末でも快適に閲覧できる形式・サイズに変換する

2026年9月22日に旧同期ジョブ（pv-sync）がfire-runnerから除去されて以降、フランからクラウドへの同期が停止している。フランには約3,744枚・5.15GBの画像があり、クラウドには初回同期時の約400枚のみが残る。本改修は同期を再開し、ユーザーが選んだフォルダの画像をクラウドで快適に閲覧できる状態を実現する。

---

## 2. 現状の整理

### 2.1 同期の停止

pv-syncはai-family-foundationリポジトリの独立スクリプトで、fire-runnerにより毎日12:00に実行されていた。2026年9月22日のレガシージョブ整理で除去され、後継が未実装のまま停止中。2026年9月2日の初回同期で507枚がアップロードされた。

v1.3で定義されていた選択ルール（直近30日＋お気に入り、5GB上限）は未実装のまま残っている。インベントリAPIは全画像を返し、`sync.recent_days`設定は使われていない。本改修のフォルダ選択（R-1）は、この未実装の選択ルールに代わる仕組みとなる。

### 2.2 クラウドのデータ構成

| 要素 | 保存先 | 形式 |
|------|--------|------|
| メタデータ | D1 | 平文 |
| 画像本体 | R2 | オリジナルPNG、AES-256-GCM暗号化 |
| サムネイル | R2 | WebP（長辺300px、品質80）、同暗号化 |

Worker側では復号しない。クライアントがvault keyで復号してBlob URLを生成する。

画像の流入経路:

- **フランからの転送**: sharpで変換、暗号化して送信
- **クラウドキューによる生成**: Durable Object（PvQueue）がNovelAI APIを呼び、R2に直接保存。`thumb_ok=0`でサムネイルなし

### 2.3 ストレージ制約

R2の容量上限は5GB（`sync.r2_limit_gb`設定値）。転送開始時に一度チェックし、超過時はその回の全アップロードをスキップする。クラウド生成やブラウザからのサムネイルアップロードはチェック対象外。アルバムでの削除操作はD1の`deleted_at`フラグを更新するのみで、R2オブジェクトは残存する。

### 2.4 計測値

画像の総量:

| 指標 | 値 |
|------|-----|
| 画像総数 | 3,744枚 |
| 合計サイズ（PNG） | 5.15GB |
| 平均サイズ（PNG） | 1,443KB |
| 最大サイズ | 3.6MB |
| 主要解像度 | 1216×832（2,654枚）、1024×1024（615枚）、832×1216（389枚） |

変換フォーマット別の推定:

| 形式（sharp変換） | 平均サイズ | 全体推定 | 対PNG比 |
|-------------------|-----------|----------|---------|
| WebP q80（原寸） | 102KB | 約370MB | 7% |
| WebP q70（原寸） | 81KB | 約300MB | 6% |
| WebP q75（長辺1024px） | 65KB | 約240MB | 4% |

PNG→WebPのフォーマット変換が圧縮の93%を担う。リサイズの追加効果は限定的。

### 2.5 現行の表示パイプライン

クラウドモードでの画像表示は以下の流れ:

1. 暗号化された画像をフェッチ
2. クライアント側でvault keyにより復号
3. Blob URLを生成して`<img>`に設定

サムネイルのキャッシュ探索順序: メモリ → IndexedDB → サーバーフェッチ。`thumb_ok=0`の画像についてはフルサイズPNGをダウンロードし、ブラウザ内で200px WebPを生成してクラウドへアップロードする。ビューアではサムネイルを先行表示し、フルサイズPNGに差し替える。中間サイズの画像やプリフェッチの仕組みは存在しない。

## 3. 要求事項

Issue #115の要求を以下のように解釈した。

### R-1: フォルダ単位のクラウド同期選択

フランの画像フォルダに接続しているとき、フォルダごとにクラウドへの同期を行うかどうかを選択できるUIを設ける。ユーザーは同期したいフォルダだけを選び、選ばなかったフォルダの画像はフランのローカルにのみ保持する。

**趣旨**: 全3,744枚を一律に同期する必要はない。ユーザーが必要なフォルダだけを選択することで、ストレージ消費と同期時間を抑え、クラウド側のアルバムを実用的な規模に保つ。v1.3で定義されたが未実装の期間・お気に入りベースの選択ルールに代わり、フォルダという直感的な粒度で制御する。

### R-2: クラウド画像の軽量化

クラウドに保存する画像を縮小・圧縮し、モバイル端末でも快適に閲覧できるようにする。現行のフルサイズ暗号化PNG（平均1,443KB）に代えて、表示に最適化した軽量フォーマットを用いる。

**趣旨**: 現行の表示パイプラインでは、閲覧のたびにフルサイズPNGをダウンロード・復号しており、モバイルでの表示が遅い。フォーマット変換だけでサイズを93%削減できる計測結果があり、閲覧体験を大幅に改善できる。クラウドはあくまで閲覧用であり、原寸PNG（正本）はフランが保持する。

### 背景（Issue R-3）

クラウドに約400枚、フランに約3,000枚の未同期画像がある。モバイル（Pixel）での表示も重い。これらの状態を解消し、ユーザーが選んだフォルダの画像をクラウドで快適に閲覧できるようにする。

## 4. 設計判断の提案

Issue #115に列挙された未決事項（D-1〜D-7）について、技術的根拠を添えて提案し、発注者の判断を得た。以下は判断反映後の内容である。

### D-1: 表示用画像のフォーマットと品質

**決定: WebP、品質80、原寸（リサイズなし）**

- フォーマット変換（PNG→WebP）だけで93%の圧縮を達成（平均1,443KB → 102KB）
- リサイズを加えても追加の圧縮は限定的（102KB → 65KB）。原画が主に1216×832でモバイルに十分な解像度であり、縮小のメリットが画質低下に見合わない
- 全画像をWebP q80で変換しても推定370MBで、R2の5GB上限に対して十分な余裕がある
- 品質80はWebPの一般的な推奨値。視覚的な劣化がほぼ認識されない水準
- サムネイル（長辺300px、品質80）は既存仕様を踏襲する

**代替案**: 品質70（推定300MB）は容量をさらに節約できるが、品質80でも余裕があるため、画質を優先する方が妥当と考える。

### D-2: クラウドのオリジナルPNG保持

**決定: 保持しない。表示用WebP＋サムネイルのみとする**

- フランがオリジナルPNGの正本を保持しており（P-10）、クラウドに複製を置く必要がない
- オリジナルPNGを残すと全量で5.15GBとなり、R2の5GB上限を超過する
- 原寸復元が必要な場面ではフラン接続時にオリジナルを取得できる
- 表示用WebP（原寸・品質80）で閲覧品質は確保される

**帰結**: R2上の既存の暗号化PNG（約400枚分）およびD1のメタデータは保全不要。表示用WebPへの移行時に上書き・削除してよい（発注者判断済み）。

### D-3: 同期対象外フォルダのクラウド側処理

**決定: クラウドから削除しない（発注者判断済み）**

一度クラウドに同期された画像はそのまま残す。フォルダの同期選択は「今後どのフォルダの新規・更新画像をクラウドへ転送するか」を制御するものであり、既にクラウドにある画像の削除とは切り離す。

- クラウドの画像は蓄積される方向となるが、表示用WebP（平均102KB）であれば全3,744枚でも推定370MBで、R2の5GB上限に対して十分な余裕がある
- ユーザーがクラウドのアルバムから個別に画像を消す操作は既存機能（`deleted_at`フラグ）で対応済み

### D-4: 同期トリガー

**決定: 手動ボタンのみ（発注者判断済み）**

ユーザーが意図したタイミングで同期を実行する。旧pv-syncの自動定期実行は採用しない。

- 実装が単純で、意図しない同期が走らない
- 同期の頻度はユーザーの裁量に委ねる

### D-5: 子フォルダの継承

**決定: 同期選択は最上位フォルダ単位。子フォルダは自動的に含める**

- ギャラリーのフォルダ構造はカードの`useAsFolder`設定で決まり、通常は1階層（例: `キャラA/`）
- 子フォルダごとの個別制御は複雑さに見合う利用場面が限定的
- 最上位フォルダ単位の選択が最も直感的で、操作が煩雑にならない

### D-6: クラウド生成画像の扱い

**決定: 本改修のスコープ外とし、別途判断する**

- クラウド生成画像はフランに存在しない（R2にのみ存在）ため、「フランからクラウドへの同期」の枠組みに収まらない
- 現在クラウドキューのR2取り込み自体が実質停止している（`thumb_ok=0`のまま放置）
- クラウド生成画像の今後の運用方針（フランへの逆同期、クラウド単独保持、廃止等）によって設計が変わる
- フォルダ同期選択の仕組みとは独立した判断が必要

発注者がスコープに含めると判断した場合は要件を追加する。

### D-7: 同期の実行主体

**決定: フランのprompt-vaultサーバー**

- フランはsharp（画像変換）、画像ファイル本体、vault key（暗号化鍵）をすべて保有している
- 旧pv-syncはai-family-foundationリポジトリの独立スクリプトで、fire-runnerに依存していた。サーバー内蔵にすることで外部依存を解消し、運用を単純化できる
- クラウドWorker側での画像変換はCPU制限（Cloudflare Workersの実行時間制限）があり、大量画像の変換には向かない

**帰結**: 旧pv-sync（ai-family-foundation）は廃止対象となる。同期契約v1.0の更新が必要になる。

## 5. 制約事項

本改修は以下の制約のもとで設計・実装する。

1. **二路構成の維持** — フラン側（Node.js + Express + better-sqlite3 + sharp）とクラウド側（Cloudflare Workers + D1 + R2 + Durable Objects）の構成を変更しない
2. **暗号化の維持** — クラウド上の画像はAES-256-GCMで暗号化する。Worker側での復号は行わない
3. **R2容量上限** — 5GB。表示用WebP化により大幅な余裕が生まれる見込み（推定370MB）
4. **フロント共通** — SPA/PWAのフロントはフラン接続・クラウド接続の両方で同じ画面を使う
5. **接続設計原則** — エンドポイントはアプリ所有。ユーザーが設定するのはCloud Token / Vault Keyのみ
6. **P-10 単一正本** — 画像の正本はフラン。クラウドは表示用の派生データを保持する
7. **鍵・トークン管理** — 鍵・トークンをソースコードや.env.exampleにハードコードしない

## 6. 関連する既知の不具合

Issue #115のコード調査で以下の不具合が疑われている（未再現）。本改修の表示パイプライン変更に伴い、対処を検討する価値がある。

| # | 内容 | 本改修との関連 |
|---|------|----------------|
| B-1 | ビューアでサムネイル取得が404になるとローディングが解除されない | 表示パイプライン変更時に合わせて対処が望ましい |
| B-2 | 新規画像のフォルダプレビューが空になる（サムネイル未生成時） | 同上 |
| B-3 | グリッドのサムネイルキャッシュのBlob URLが解放されず、モバイルのメモリを圧迫する | 表示パイプライン改修で根本対処が可能 |
| B-4 | `/thumbs` GETが暗号化バイト列を`image/webp`のContent-Typeで返す | 表示への実害なし。優先度低 |

B-1〜B-3は表示パイプラインの変更と密接に関連しており、本改修のスコープに含める（S-1、発注者判断済み）。B-4は表示への実害がなく優先度が低いため、対象外とする。

## 8. スコープ外

以下は本改修のスコープに含めない。

- クラウドからフランへの逆方向同期
- NovelAI API の画像生成機能への変更
- カード・プリセット・キューの機能変更
- フロントのフラン接続モードへの変更
- クラウドWorkerのアーキテクチャ変更（D1/R2/Durable Objectsの構成変更）
